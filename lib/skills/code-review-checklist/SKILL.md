# Code Review Checklist

機械化的 code review 流程。每項都是 yes/no 判斷，不是主觀評估。任一失敗即 `verdict: fail`，於 `checks[]` 列具體 evidence。

## 1. Diff 範圍對齊

**動作**：
```bash
git diff main...HEAD --name-only
```

**檢查**：每個改動檔是否在 `plan.allowed_paths` 裡？

**通過條件**：100% 在範圍內。範圍外改動 → fail。

**Evidence 格式**：
```
out_of_scope: [services/billing/api.go]
allowed_paths: [services/user/**, services/auth/**]
```

## 2. 測試結果

**動作**：跑 recipe 設的 `test_command`。

**通過條件**：
- 全 pass，或
- 失敗的測試是 baseline（pre-existing fail，main branch 也壞）

**baseline 判定**：
```bash
git stash    # 暫存改動
git checkout main
{test_command}     # 跑 baseline
git checkout -    # 回 worktree branch
git stash pop
```
若 baseline 也 fail → 該測試屬 baseline，不算本次 regression。

**Evidence 格式**：
```
new_failures: [tests/test_user.py::test_login]
baseline_failures: [tests/test_legacy.py::test_old]   # ignored
```

## 3. Lint

**動作**：跑 recipe 設的 `lint_command`。

**通過條件**：無新增 error（baseline 比對同上）。

**Evidence**：
```
new_lint_errors: 2
files: [services/user/handler.py:45, services/auth/middleware.py:12]
```

## 4. 新依賴

**動作**：
```bash
git diff main...HEAD pyproject.toml package.json go.mod Cargo.toml
```
（依語言生態系挑對應檔）

**通過條件**：
- 無 diff → pass
- 有 diff 但 plan 明確許可 → pass
- 有 diff 且 plan 未提 → **不是 fail，是 needs_dependency verdict**（producer 該回的，reviewer 偵測到 producer 漏標 → fail）

**Evidence**：
```
new_deps: [{"name": "cryptography", "version": ">=42.0", "ecosystem": "pip"}]
plan_authorized: false
```

## 5. Hook 繞過

**動作**：
```bash
git log main..HEAD --grep "no-verify\|skip-hook\|--amend" --all
```

**通過條件**：無匹配。

**Evidence**：
```
suspicious_commits: [<sha>: <message>]
```

## 6. 介面穩定

**動作**：依語言判斷哪些是 public API，diff 是否動到。

| 語言 | Public API 判定 |
|---|---|
| Python | `def {name}` not starting with `_`, class methods 同樣 |
| Go | 大寫開頭的 func / struct field |
| TypeScript | `export` 標記的 |
| Rust | `pub fn` / `pub struct` |
| HTTP API | OpenAPI / 路由定義檔 |

**通過條件**：
- 無動到 public API → pass
- 動到但 plan 介面契約章節許可 → pass
- 動到且 plan 未提 → fail

**Evidence**：
```
breaking_changes:
  - file: services/user/api.go
    symbol: GetUser
    change: "param signature: (id string) → (id string, ctx context.Context)"
plan_authorized: false
```

## 7. Commit Message 規範

**動作**：
```bash
git log main..HEAD --oneline
```

**通過條件**：
- 每 commit 主旨 ≤ 72 字
- 無 "Generated by..." / "Co-Authored-By: Claude" 字樣
- 無單字 "fix" / "wip" / "test" 這類無資訊主旨

**Evidence**：
```
violations:
  - <sha>: "fix" (no information)
  - <sha>: "...(超過 72 字...)"
```

## 8. WIP 殘留

**動作**：
```bash
git diff main...HEAD | grep -nE "TODO|FIXME|XXX|console\.log|print\(|debugger"
```
（依語言調整）

**通過條件**：
- 無匹配，或
- 匹配的 TODO 被 plan 明確接受

**Evidence**：
```
wip_markers:
  - services/user/handler.py:67: "// TODO: handle edge case"
plan_authorized: false
```

## 9. 自評誠實

**動作**：對比 `engineer.output.md` 的「變動摘要」與實際 git diff。

**通過條件**：自評描述與實際變動一致（沒漏寫、沒謊報）。

**Evidence**：
```
unreported_changes: [services/cache/invalidation.go - 改了 30 行未在 output.md 提及]
```

## 10. 無破壞性結構變動

**動作**：
```bash
git diff main...HEAD --stat | tail -1
```

**通過條件**：
- 改動規模在 plan estimated_complexity 預期內
- 不超過 estimated_complexity 預期 3 倍（small ≤ 50 行 / medium ≤ 200 行 / large ≤ 600 行）
- 超過 → fail（建議 needs_decomposition）

**Evidence**：
```
total_changed: 850 lines
estimated_complexity: small (≤50 expected)
ratio_exceeded: 17x
```

## 11. Plan↔Code 命名 / 契約對齊

**動作**：從 plan 的「介面契約」「範圍」章節抽出對外命名（型別 / 函式 / cmd / struct / RPC 名），grep 實際 code 確認存在且一致。

**通過條件**：
- code 的對外命名與結構與 plan 描述一致 → pass
- 不一致且 plan 未授權 engineer 自訂命名 → fail（doc drift：plan 寫 `LobbyDataSource`，code 變 `PGameConfigClient`，未來 engineer 讀 plan 會被誤導）

**Evidence**：
```
plan_says: ["LobbyDataSource", "FakeLobbyDataSource", "Wrapper"]
code_has:  ["PGameConfigClient", "MockPGameConfigClient", "GRPCClient"]
drift: 3 symbols renamed, plan not updated
```

## 12. 跨檔 Wiring 完整性

**動作**：對本次新增 / 改名的 config key、env var、registration symbol（任何「需在多個檔案同步出現才生效」的東西），grep 其所有應出現的 wiring 點。

```bash
git grep -n "<symbol>"   # 例 projectConfigMap / PGAME_CONFIG_SERVICE_ADDR
```

**通過條件**：所有 wiring 點都接上。「加了 config struct field + reader 卻漏接 registration map」即 fail（這類漏接 unit test 抓不到，只有 runtime / localTest 會 panic）。

**Evidence**：
```
symbol: PGAME_CONFIG_SERVICE_ADDR
wired:   [config/file.go ✓, server.go ✓, Configuration struct ✓]
missing: [main.go::projectConfigMap ✗]   ← fail
```

## 13. 註解紀律

**動作**：Read diff 內新增 / 改動的註解（含被改段落附近的既有註解）。

**通過條件**：
- 無 WHAT 註解（重述 code 在做什麼，例 `// loop over games`）
- 留下的註解對應**當前** code，無「code 改了註解沒改」的 drift
- 業務 / WHY 註解內容正確（不誤導）

**Evidence**：
```
redundant_what: [manager.go:88 "// increment counter"]
stale: [common.go:42 註解寫 "fallback to en" 但 code 已改 fallback defaultLang]
```

## 執行順序

reviewer 應依此順序跑：

1. Diff 範圍（fail-fast：範圍不對其他不用看）
2. 規模（fail-fast：規模爆炸建議拆 brief）
3. Hook 繞過（高風險）
4. 新依賴
5. 介面穩定
6. 測試
7. Lint
8. WIP 殘留
9. Commit message
10. 自評誠實
11. Plan↔code 命名 / 契約對齊
12. 跨檔 wiring 完整性
13. 註解紀律

任一 step fail → 立即 emit verdict: fail，不再跑後續（節省 token）。

注意：§11-13 是語意層檢查（對齊 / wiring / 註解），不像 §1-2 能 fail-fast。即使 §1-10 全 pass 也必跑——它們正是「checklist 全綠卻在 holistic / 逐行 review 才爆」的那類問題的攔截點。

## verdict 範例

```json
{
  "verdict": "fail",
  "checks": [
    {"name": "diff_scope", "result": "pass", "evidence": "all 8 files in allowed_paths"},
    {"name": "size", "result": "pass", "evidence": "47 lines, within small expected"},
    {"name": "hook_bypass", "result": "pass", "evidence": "no --no-verify commits"},
    {"name": "new_deps", "result": "pass", "evidence": "no dep file changes"},
    {"name": "interface_stability", "result": "fail", "evidence": "GetUser signature changed in services/user/api.go:23, not authorized in plan"}
  ]
}
```
